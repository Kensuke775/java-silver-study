
### 2.8 境界付きワイルドカード型 (PECS)

- 上限境界 `<? extends T>`: Tまたはそのサブタイプ。**取得(get)は安全、追加(add)はnullのみ**(Producer=extendsはget専用、と覚える)。

- 下限境界 `<? super T>`: Tまたはそのスーパータイプ。**追加(add)はTの型まで安全、取得(get)はObject型**(Consumer=superはadd専用、と覚える)。

- 通称 **PECS (Producer Extends, Consumer Super)**。「取り出す(読む)用途ならextends、詰め込む(書く)用途ならsuper」。

- 表1-2の対応(教科書内):

| 構文              | 要素の追加(add) | 要素の取得(get) |
| --------------- | ---------- | ---------- |
| `<?>`           | nullのみ     | Object型    |
| `<? extends T>` | nullのみ     | T型         |
| `<? super T>`   | T型まで       | Object型    |

**メモ(並行して進めている出題セッションの例題より)**: 教科書は`List<T>`での説明だったが、`Box<T>`のような自作の任意のジェネリッククラスでも全く同じ理屈が成り立つ。

- `Box<? extends Number>` — 「Numberか、その何らかのサブタイプ」

  - 実際の型は`Box<Integer>`かもしれないし`Box<Double>`かもしれない。コンパイラにはどのサブタイプか分からない。

  - `get()`は安全: 中身が何であれ、少なくとも`Number`ではあることが保証されているので、`Number n = box.get();`はOK。

  - `set()`は基本的に不可: もし実際は`Box<Double>`なのに`box.set(10)`(Integerを入れる)を許してしまうと、型の整合性が壊れる。コンパイラは「実際の型が何か分からない」ので、安全側に倒してnull以外の`set()`を一切禁止する。

  - まとめ: 「取り出すのは安全、入れるのはほぼ不可能」→ 読み取り専用として使う場面向け。

- `Box<? super Integer>` — 「Integerか、その何らかのスーパータイプ」

  - 実際の型は`Box<Integer>`かもしれないし`Box<Number>`、`Box<Object>`かもしれない。

  - `set()`は安全: `Integer`(またはそのサブタイプ)を入れる分には、相手がInteger/Number/Objectのどれであっても必ず受け入れられるので、`box.set(10)`はOK。

  - `get()`はObjectとしてしか受け取れない: 実際の型がどこまで上位か分からないので、コンパイラは「少なくともObjectではある」としか保証できない。`Number n = box.get();`のようにObjectより具体的な型に代入しようとするとコンパイルエラーになる(`Object o = box.get();`ならOK)。

  - まとめ: 「入れるのは安全、取り出すのはObjectとしてのみ」→ 書き込み専用として使う場面向け。

**疑問(問題4-2の`? extends Number` / `? super Integer`をめぐる深掘り)**:

- 質問: `Box<? extends Number> box1 = new Box<Integer>();`で、宣言側の`Number`と実体`new Box<Integer>()`の`Integer`が別々なのがピンとこない。

- 回答: 3行目には実は2つの型が登場している。

  ```java
  3  Box<? extends Number> box1 = new Box<Integer>();
     └──────左辺(変数の型)──────┘   └─右辺(実際に作られる箱)─┘
  ```

  - 右辺`new Box<Integer>()`: 実際に生成されるオブジェクトの型。`Integer`専用の箱として確定している。

  - 左辺`Box<? extends Number>`: 変数`box1`という「入れ物」の宣言上の型。`Integer`専用とは書いておらず、「`Number`かそのサブタイプの、何かの箱」とぼかしている。

  `Box<? extends Number>`は「実体の型を制限する」のではなく「**変数がその実体についてどこまで知ることを許すか**」を制限する仕組み。主にメソッドの引数として使い、「Numberのサブタイプなら何のBoxでも受け取りたい」という汎用性を持たせるために使う(例: `static void printBoxValue(Box<? extends Number> box)`なら`Box<Integer>`でも`Box<Double>`でも渡せる)。

- 質問: `? super Integer`が呼び出せるのは、Integer→Number→Objectという継承関係で、Numberの方がより広い存在だから?

- 回答: その通り。継承階層は`Integer → Number → Object`(下から上に「広くなる」)。`Box<? super Integer>`は「`Integer`、またはそれより広い(先祖側)型のBox」という意味で、対象になるのは`Box<Integer>` / `Box<Number>` / `Box<Object>`。ただし正確には継承チェーンだけでなく、`Integer`が実装しているインタフェースも候補に含まれる。`javac`で検証済み:

  ```java
  Box<? super Integer> b1 = new Box<Integer>();               // OK
  Box<? super Integer> b2 = new Box<Number>();                 // OK
  Box<? super Integer> b3 = new Box<Object>();                 // OK
  Box<? super Integer> b4 = new Box<Comparable<Integer>>();    // OK(Integerが実装するインタフェース)
  Box<? super Integer> b5 = new Box<java.io.Serializable>();   // OK(同上)

  Box<? super Integer> b6 = new Box<Double>();  // エラー
  // 不適合な型: Box<Double>をBox<? super Integer>に変換できません
  ```

  試験対策としては`{Integer, Number, Object}`という継承チェーンで押さえておけば十分だが、`Double`のような「兄弟(同じ親を持つが継承関係にない型)」は候補に入らない、という感覚が本筋。

- 質問: set/getの可否は結局何を基準に決まっているのか?

- 回答: 基準は「**`?`が実際にどの候補の型であっても、その操作が矛盾なく成り立つか**」の一点。「わからないから禁止」ではなく「候補を全部試しても壊れないなら許可」という考え方。

  `Box<? extends Number>`(候補`{Number, Integer, Double, Long, ...}`)の場合:

  ```
  get(): 実体がInteger/Double/Longのどれでも → 取り出したものは必ずNumber → 矛盾なし → 許可
  set(10): 実体がInteger → OK / 実体がDouble → Integer混入で矛盾 / 実体がLong → 同様に矛盾
           → 候補によって結果が食い違う → 禁止
  ```

  `Box<? super Integer>`(候補`{Integer, Number, Object, ...}`)の場合:

  ```
  set(10): 実体がInteger/Number/Objectのどれでも → Integerは必ず入る → 矛盾なし → 許可
  get()をNumberで受ける: 実体がObject → 中身はString等の可能性もありNumberとは限らない
                        → 候補によって結果が食い違う → 禁止(Objectとしてなら常に成立するのでOK)
  ```

- 質問(9行目`Number n2 = box2.get();`が成立しない理由): なぜ`Number`で受け取れないのか?

- 回答: 候補`{Integer, Number, Object, ...}`の中から極端な例`Box<Object>`を考える。

  ```java
  Box<? super Integer> box2 = new Box<Object>();   // これも合法な候補の1つ
  box2.set(10);                                     // OK: Integerはどの候補にも入る
  box2.set("hello");                                 // これもOK: Object専用の箱だから文字列も入る

  Number n2 = box2.get();   // 実体がBox<Object>なら中身がStringの可能性もある → 矛盾
  ```

  `box2`の実体が`Object`専用の箱だった場合、`get()`が返す値は`Integer`とは限らず`String`かもしれない。コンパイラはどの候補が実体か判断できないため、「候補のどれであっても矛盾なく成り立つか」という基準に照らすと`Number`型で受け取ることは`Box<Object>`という候補で破綻する。どの候補でも共通して保証できるのは「少なくとも何らかのオブジェクトではある」という`Object`のみなので、`get()`は`Object`型としてしか受け取れない。

  まとめ: `set()`はどの候補でも`Integer`を受け入れられるので許可される一方、`get()`は候補によって返ってくる値の具体的な型がバラバラなので、全候補に共通する最低限の型である`Object`としてしか受け取れない。

**教科書の例(`chap1/10`: 標準`List`でのPECS確認)**:

```java
 1  import java.util.ArrayList;
 2  import java.util.List;
 3
 4  public class Main {
 5      static void testUpperBnd(List<? extends Number> list) {
 6          list.add(null);
 7       // list.add(Integer.valueOf(10));
 8          Number n = list.get(0);
 9      }
10      static void testLowerBnd(List<? super Number> list) {
11          list.add(Integer.valueOf(10));
12       // list.add(new Object());
13          Object o = list.get(0);
14       // Number n = list.get(1); Integer i = list.get(2);
15      }
16      public static void main(String[] args) {
17          List<Object> oList = new ArrayList<>(); oList.add(1);
18          List<Number> nList = new ArrayList<>(); nList.add(1);
19          List<Integer> iList = new ArrayList<>(); iList.add(1);
20       // testUpperBnd(oList);
21          testUpperBnd(nList);
22          testUpperBnd(iList);
23          testLowerBnd(oList);
24          testLowerBnd(nList);
25       // testLowerBnd(iList);
26      }
27  }
```

**説明したポイント**

- `Box`の例と同じ理屈を教科書標準の`List`で確認するもの。

- 5〜9行目 `testUpperBnd(List<? extends Number> list)`: 上限境界。`get(0)`は`Number`として安全に取り出せる(8行目)が、`add()`は`null`以外禁止(7行目、`Integer.valueOf(10)`ですらエラーになる例)。

- 10〜14行目 `testLowerBnd(List<? super Number> list)`: 下限境界。`add(Integer.valueOf(10))`はOK(11行目、`Number`のサブタイプなのでどの候補でも受け入れられる)。`get(0)`は`Object`型でしか受けられない(13行目)。14行目コメントは`Number`/`Integer`で受けようとするとエラーになる例。

- 20行目: `testUpperBnd(oList)`(`List<Object>`)がコメントアウトされている理由は、`Object`は`Number`のサブタイプではない(むしろスーパータイプ)ため、`? extends Number`の候補に含まれないから。

- 21〜22行目: `nList`(`List<Number>`)、`iList`(`List<Integer>`)はどちらも`Number`かそのサブタイプなので`testUpperBnd`に渡せる。

- 23〜24行目: `oList`、`nList`は`Number`かそのスーパータイプなので`testLowerBnd`に渡せる。

- 25行目: `testLowerBnd(iList)`がコメントアウトされている理由は、`Integer`は`Number`のサブタイプであって、スーパータイプではないため`? super Number`の候補に含まれないから。

**まとめ: `<T> void copy(List<? super T> dest, List<? extends T> src)`のような2引数ワイルドカードから`T`を逆算する方法(かなり難しかったポイント)**

`Box<? extends Number>`のようにワイルドカードの相手(`Number`)が具体的な型で固定されている場合は、「`?`(実際の型)の範囲」を求めるだけで済む。しかし`copy(List<? super T> dest, List<? extends T> src)`のように相手が**まだ決まっていない型パラメータ`T`自身**の場合、実引数(`dest`/`src`に渡した具体的な型)から**`T`を逆算する**という一段余分な思考が必要になり、ここで実際に何度も混乱した。

**つまずいた点**: `extends`は「サブタイプ方向」という理解自体は正しいが、それは常に「`?`(実際の型)が`T`から見てサブタイプ側にある」という意味でしかない。実引数が先に分かっていて`T`を求めるときは、この不等式を`T`について解く形になるため、**向きが逆に見える**。

```
List<? extends T> の意味:      実際の型 ≦ T   (実際の型はTかそれ以下)
List<? super T>   の意味:      実際の型 ≧ T   (実際の型はTかそれ以上)
```

これは方程式`a ≦ b`と同じで、「`b`が既知で`a`を求める」場合と「`a`が既知で`b`を求める」場合とで答えの言い回し(以上/以下)が反転するのと同じ現象。ルール自体(`a ≦ b`)は変わっていない。

**実際の逆算手順**:

1. `src`(`List<? extends T>`)に渡した実際の型を`X`とすると、`X ≦ T` → **`T`は`X`以上**(`T`の下限)。
2. `dest`(`List<? super T>`)に渡した実際の型を`Y`とすると、`Y ≧ T` → **`T`は`Y`以下**(`T`の上限)。
3. 「`T`の下限`X`」と「`T`の上限`Y`」が矛盾なく重なる(`X ≦ Y`が成り立つ)なら、その範囲内の`T`(通常は`X`)でコンパイルが通る。重ならない(`X`が`Y`より上位)なら、どんな`T`も両方を満たせずコンパイルエラーになる。

**具体例(問題10-2, 10-3で検証済み)**:

| 呼び出し | src(下限) | dest(上限) | 判定 |
|---|---|---|---|
| `copy(Number型dest, Integer型src)` | Integer以上 | Number以下 | Integer ≦ Number → 重なりあり(T=Integer) → OK |
| `copy(Integer型dest, Number型src)` | Number以上 | Integer以下 | NumberはIntegerより上位 → 重なりなし → **コンパイルエラー** |
| `copy(Integer型dest, Double型src)` | Double以上 | Integer以下 | IntegerとDoubleは兄弟(共通の親Numberを持つだけ) → 重なりなし → **コンパイルエラー** |

一番わかりやすい判定法: **「`dest`の実際の型」が「`src`の実際の型」のスーパータイプ(または同じ型)になっているか**をチェックするだけでよい。`src`は下限、`dest`は上限なので、`dest ≧ src`という関係(継承階層で`dest`が`src`と同じか上)が成り立っていれば必ずコンパイルが通り、成り立たなければ(`dest`が`src`より下位、または`src`と無関係な兄弟型)コンパイルエラーになる。

## この単元でよくある引っかけパターン(自己チェック用ヒント)

次の観点を自分の言葉で説明できるか確認してみてください。答え合わせはせず、まず自分で考えること。

1. **raw型を経由すると何が起きるか？** — `Box box = new Box(); box.set(10);` は型的に何が保証されなくなる？コンパイルは通る？警告は出る？

2. **static文脈と型パラメータ** — クラスの型パラメータ`T`をstaticフィールドやstaticメソッドの引数に直接使えないのはなぜ？一方でstaticなジェネリックメソッド`<E> static void bar(...)`はなぜ許されるのか、両者の違いを説明できるか。

3. **配列とジェネリクスの共変性の違い** — `Number[] arr = new Integer[3];`はコンパイルが通るのに、`List<Number> list = new ArrayList<Integer>();`はなぜコンパイルエラーになるのか。実行時エラーのリスクの所在がどう違うか。

4. **`List<?>`に`add(null)`だけが許される理由** — nullがなぜ唯一の例外なのか、型安全性の観点から説明できるか。

5. **PECSの根拠** — `<? extends Number>`でaddができない理由と、`<? super Number>`でgetがObject型になる理由を、それぞれ「コンパイラが具体的に何を知らないか」から説明できるか。

6. **ダイヤモンド演算子の省略可否** — 省略できる場所とできない場所を、宣言側/生成側という軸で言い分けられるか。
