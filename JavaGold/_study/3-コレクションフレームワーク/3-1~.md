### 3. コレクションフレームワーク / 4.1 List インタフェース

**教科書の例(**`chap1/11`**):**

```java
 1  import java.util.ArrayList;
 2  import java.util.List;
 3
 4  public class Main {
 5      public static void main(String[] args) {
 6          List<Integer> list = new ArrayList<>();
 7          list.add(10); list.add(20); list.add(null);
 8          for (Integer i : list) System.out.print(i + " ");
 9          System.out.println("\nsize(): " + list.size());
10          System.out.println("set() : " + list.set(2, 20));
11          System.out.println("contains(): " + list.contains(50));
12          System.out.println("indexOf() : " + list.indexOf(20));
13          System.out.println(list);
14          list.add(0, 100);
15          System.out.println("remove(): " + list.remove(1));
16          System.out.println("remove(): "
17                          + list.remove(Integer.valueOf(20)));
18       // System.out.println("remove(): " + list.remove(20));
19          System.out.println(list);
20      }
21  }
```

**説明したポイント**

- 7行目: `list.add(10); list.add(20); list.add(null);` の時点で中身は `[10, 20, null]`。
- 10行目: `set(2, 20)` はインデックス2の要素を`20`に**置き換えて**、**置き換え前の古い値を返す**メソッド。このケースでは元々`null`が入っていたので`null`が返る(置き換え後は`[10, 20, 20]`)。
- 14行目: `add(0, 100)` は「インデックス0の**位置に挿入**」。既存要素は後ろにずれる(結果は`[100, 10, 20, 20]`)。
- 15〜18行目が最大の引っかけどころ。`remove()`には2種類のオーバーロードがある。
  - `remove(int index)` : インデックス指定で削除し、**削除された要素**を返す。
  - `remove(Object o)` : 値(オブジェクト)指定で削除し、**削除できたかどうか(boolean)**を返す。
- 15行目 `list.remove(1)` は引数が`int`リテラルなので**インデックス版**が呼ばれる。インデックス1の要素(`10`)を削除して返す(結果は`[100, 20, 20]`)。
- 17行目 `list.remove(Integer.valueOf(20))` は引数が`Integer`オブジェクトなので**値版**が呼ばれる。最初に見つかった`20`を削除する(結果は`[100, 20]`)。
- 18行目のコメントアウト `list.remove(20)` は、もし生かすと引数が`int`リテラルのままなので**インデックス版**として解決されてしまう(値としての`20`を消したいつもりでも、オートボクシングされず`int`のままオーバーロード解決される)。この時点で`list`のサイズは2しかないため、インデックス20を指定すると`IndexOutOfBoundsException`が起きる。

**セクションの核心**

`remove()`のオーバーロード解決は「引数の**コンパイル時の型**が`int`か`Integer`か」で決まる。`int`ならインデックス版、`Integer`(または他のオブジェクト型)なら値版。オートボクシングは「他に一致するメソッドが無い場合の最終手段」としてしか働かないため、`int`引数がある限り優先してインデックス版が選ばれる、という点が試験でも実務でも間違えやすいポイント。

### Listの主な実装クラス: ArrayList / LinkedList / Vector

```
        interface
         List<E>

ArrayList<E>   LinkedList<E>   Vector<E>
```

**ArrayList**

- 内部に**配列**を使って要素を保持する。
- インデックス指定でのアクセス(ランダムアクセス)は高速。
- ただし配列の途中への挿入・削除は、それ以降の要素をずらす必要があるため、要素数が多い場面ではパフォーマンスが低下する。
- **スレッドセーフではない**(複数スレッドから同時にアクセスする場合の安全性は保証されない)。

**LinkedList**

- **双方向リンクリスト**で要素を保持しており、各要素が前後の要素へのリンク情報を持っている。
- インデックス指定でアクセスする際は、先頭(または末尾)から順にリンクを辿る必要があるため時間がかかる。
- 一方、要素の追加・削除(特に先頭・末尾付近)は、`ArrayList`のように配列全体をずらす必要がなく、**リンクを繋ぎ変えるだけ**で済むため高速。
- こちらも`ArrayList`と同様に**スレッドセーフではない**。

**Vector**

- コレクションフレームワーク登場(Java 1.2)以前からある**レガシークラス**。
- `ArrayList`と同じ内部構造(配列)を持つが、各メソッドが`synchronized`されているため**スレッドセーフ**。
- ただしスレッドセーフである代償として、`ArrayList`よりパフォーマンスは劣る。

**図1-8のイメージ(先頭への要素追加)**

- `ArrayList`: 新たな配列を生成し、既存の要素をすべて1つ後ろへずらしてから先頭に追加する(コストが高い)。
- `LinkedList`: 前後の要素のリンク情報を更新するだけで済む(コストが低い)。

**参考: コレクションのレガシー実装**

コレクションフレームワークはJava 1.2で登場した仕組み。それより前から存在する`Vector<E>`クラスや`Hashtable<K, V>`クラス(Mapの回で登場予定)は**レガシー実装**と呼ばれ、スレッドセーフな設計だった。一方、コレクションフレームワークのクラス(`ArrayList`, `LinkedList`など)はパフォーマンスを優先し、基本的に**スレッドアンセーフ**。レガシー実装は後方互換性のために残されているが、マルチスレッド環境向けには別途「並行処理コレクション」が提供されている(第5章で扱う予定)。

**セクションの核心**

3つのクラスは同じ`List<E>`インタフェースを実装していて呼び出し方(メソッド)は共通だが、内部構造(配列 vs リンクリスト)によって「ランダムアクセスの速さ」と「挿入・削除の速さ」がトレードオフの関係になっている。`Vector`はさらに「スレッドセーフかどうか」という軸が加わったレガシー版`ArrayList`、という位置づけで整理すると覚えやすい。

**疑問**:

- 質問: ランダムアクセスって何ですか?

- 回答: 「インデックス番号を指定して、いきなりその位置の要素に直接アクセスできる」という意味。対義語は「シーケンシャルアクセス(先頭から順番にしかアクセスできない)」。

  - `ArrayList`は内部が配列なので、`list.get(5)`と言われたら「先頭アドレス + 5×要素サイズ」を計算するだけで一発でその位置にたどり着ける(計算だけで済む=速い)。

  - `LinkedList`は内部がリンクリストなので、`list.get(5)`と言われても直接計算できない。先頭から1個目→2個目→3個目…と**リンクを辿って数えながら進む**しかない(=遅い)。

- 質問: `synchronized`・スレッドセーフってどういう意味ですか?

- 回答: `synchronized`はJavaのメソッドやブロックに付けられるキーワードで、「**同時に1つのスレッドしかここを実行できないようにロックする**」という意味。

  ```java
  public synchronized void add(E e) {
      // このメソッドの中身は、同時に1スレッドしか実行できない
  }
  ```

  複数のスレッド(≒同時並行で動く処理の流れ)が同じリストに同時に`add()`しようとすると、内部データが壊れる(要素が消える、配列が壊れる等)危険がある。`synchronized`を付けると、あるスレッドが`add()`実行中は他のスレッドが「順番待ち」になり、1つずつ処理されるので安全になる。この「複数スレッドから同時に触っても安全」という性質を**スレッドセーフ**と呼ぶ。

  - `Vector`: 全メソッドに`synchronized`が付いている → スレッドセーフ。ただし毎回ロックの取得・解放のコストがかかるので遅い。

  - `ArrayList`: `synchronized`が付いていない → スレッドセーフではない(速いが、マルチスレッドで同時に触ると壊れる可能性がある)。

  補足: 1人で書いたコードを1スレッドで動かしている現時点の学習範囲では、`synchronized`の有無は動作の違いとして表面化しない。複数スレッドが同時に同じコレクションを操作する場面(Webサーバーが複数リクエストを同時処理する等)で初めて問題になる話。

### 4.2 Set<E>インタフェース: HashSet / LinkedHashSet / TreeSet

**教科書の例(`chap1/12`):**

```java
 1  import java.util.HashSet;
 2  import java.util.LinkedHashSet;
 3  import java.util.Set;
 4  import java.util.TreeSet;
 5
 6  public class Main {
 7      public static void main(String[] args) {
 8          Set<Integer> set1 = new HashSet<>();    // HashSet
 9          boolean add1 = set1.add(3);
10         boolean add2 = set1.add(3);
11         set1.add(null); set1.add(null);
12         set1.add(2); set1.add(1);
13         System.out.println("HashSet: " + set1);
14         System.out.println(" add1: " + add1 + ", add2: " + add2);
15         boolean rmv1 = set1.remove(3);
16         boolean rmv2 = set1.remove(3);
17         System.out.println(" rmv1: " + rmv1 + ", rmv2: " + rmv2);
18         // LinkedHashSet
19         Set<Integer> set2 = new LinkedHashSet<>();
20         set2.add(3); set2.add(3);
21         set2.add(null); set2.add(null);
22         set2.add(2); set2.add(1);
23         System.out.println("LinkedHashSet: " + set2);
24         // TreeSet
25         Set<String> set3 = new TreeSet<>();
26         set3.add("Duke"); set3.add("James"); set3.add("Alice");
27         System.out.println("TreeSet: " + set3);
28     }
29  }
```

**説明したポイント**

`Set<E>`は**重複を許さない**コレクション。3つの実装クラスの違いは「**順序**」がポイントになる。

- **HashSet(8〜17行目)**: 順序を保証しない(内部のハッシュ値に基づいて格納されるため、`add()`した順とは無関係な順で並ぶ)。

  - `null`は1つだけ許容(2回目の`add(null)`は無視される)。

  - 重複値(`3`を2回`add`)も2回目は無視され、`add()`は成功したかどうかを`boolean`で返す(`add1=true`, `add2=false`)。

  - 同様に`remove()`も削除できたかを`boolean`で返す(`rmv1=true`, `rmv2=false`、1回目で既に消えているため)。

- **LinkedHashSet(19〜23行目)**: `HashSet`のサブクラス。重複禁止などの性質は同じだが、**追加した順序を保持する**。

- **TreeSet(25〜27行目)**: 要素を**自動的にソートして**格納する(`Alice, Duke, James`のようにアルファベット順になる)。

**疑問**:

- 質問: 実行結果が`HashSet: [null, 1, 2, 3]`となり、順序付けされているように見える。本当に順序は保証されていないのか?

- 回答: たまたまそう見えているだけで、順序は保証されていない。

  `HashSet`は内部的に「ハッシュテーブル」という仕組みでデータを持つ。要素を`add()`するとき、その要素の`hashCode()`の値を元に「何番目の棚(バケット)に入れるか」を計算して格納する。出力(`toString()`)時は**棚の番号順**に取り出しているだけで、「値の大小」や「追加した順」を見ているわけではない。

  今回`[null, 1, 2, 3]`のように昇順に見えるのは、次の偶然が重なっているため。

  - `Integer#hashCode()`は、その`int`の値そのものを返す(`Integer.valueOf(3).hashCode()`は`3`)。

  - `HashSet`のデフォルトの棚の数(初期容量)は`16`。

  - 棚の番号は`hashCode & (棚の数 - 1)`という計算で決まり、`0〜15`の小さい整数の場合、この計算結果は**元の値と一致してしまう**(例: `3 & 15 = 3`)。

  つまり、小さい`Integer`を入れている今回のケースに限って「棚の番号 = 値そのもの」になるため、結果的に昇順に見えているだけ。`null`が先頭に来るのも「`null`用の棚が0番目に固定されている」というJavaの実装上の都合による。

  もし`16`以上の値や負の数、`String`を入れると、この偶然の一致は崩れて順序はバラバラになる(例: `set1.add(100); set1.add(3); set1.add(50);`は昇順にならない)。`HashSet`の出力順は内部実装依存の並びであり、当てにしたコードを書かないのが鉄則。

### 4.2 Set<E>インタフェース: equals()/hashCode()と重複判定(通常クラス vs record)

**教科書の例(`chap1/13`):**

```java
 1  import java.util.HashSet;
 2  import java.util.Set;
 3
 4  class Improper {
 5      int id; String name;
 6      Improper(int id, String name) {
 7          this.id = id; this.name = name;
 8      }
 9      @Override public String toString() {
10          return "Improper[" +
11                  "id=" + id + ", name=" + name + "]";
12      }
13  }
14  record Proper(int id, String name) {}
15
16  public class Main {
17      public static void main(String[] args) {
18          Set<Improper> set1 = new HashSet<>();
19          set1.add(new Improper(1, "bad"));
20          set1.add(new Improper(1, "bad"));
21          System.out.println("HashSet with Improper : " + set1);
22          Set<Proper> set2 = new HashSet<>();
23          set2.add(new Proper(2, "good"));
24          set2.add(new Proper(2, "good"));
25          System.out.println("HashSet with Proper   : " + set2);
26      }
27  }
```

**説明したポイント**

- `Improper`クラスは`toString()`しかオーバーライドしていない(`equals()`/`hashCode()`は`Object`のデフォルトのまま)。

- `Object`のデフォルトの`equals()`は「同一インスタンスかどうか(`==`と同じ)」でしか判定しない。20行目の`new Improper(1, "bad")`は19行目とは**別のインスタンス**なので、中身が同じでも`equals()`は`false`になり、`HashSet`は「別物」として**両方とも追加してしまう**(`set1`のサイズは2)。

- 一方`record`(14行目)は、コンパイラが自動的に**フィールドの中身を比較する`equals()`/`hashCode()`を生成**する。そのため23〜24行目は「中身が同じ`Proper`」と判定され、2回目の`add()`は無視される(`set2`のサイズは1)。

- `HashSet#add()`の内部動作は2段階: ①`hashCode()`で「どの棚(バケット)に入れるか」を決める、②その棚に既に何か入っていたら、新要素と`equals()`で比較し「等しい」と判定されたものが既にあれば追加をスキップする。`Improper`は`hashCode()`もデフォルトのまま(インスタンスごとにバラバラの値)なので同じ棚に入る保証すらなく、`equals()`も別インスタンス扱いのため両方追加される。

**疑問**:

- 質問: クラスで作った場合、`equals()`は中身の比較ではないのか?

- 回答: 誤解で、逆。何もオーバーライドしていない場合、`equals()`は`Object`から継承したデフォルト実装がそのまま使われ、これは「同一インスタンスかどうか(`==`と同じ)」の判定になる。

  ```java
  Improper a = new Improper(1, "bad");
  Improper b = new Improper(1, "bad");
  a.equals(b);  // false (中身は同じでも別インスタンスだから)
  a.equals(a);  // true  (自分自身と比較すれば当然true)
  ```

  「中身を比較する`equals()`」にしたいなら、`id`と`name`を見て判定するように自分で`equals()`をオーバーライドする必要がある。`record`はこれをコンパイラが自動生成してくれる、という違い。

- 質問: `add()`する時に`equals()`が呼ばれているということか?

- 回答: その理解で正しい。`HashSet#add()`は①`hashCode()`で棚を決める→②同じ棚の既存要素と`equals()`で比較、という2段階で重複判定している。

- 質問(訂正): 「recordなら別インスタンスとしてじゃなく同一インスタンスとして書き込まれるから、Setの役割を果たす」という理解で合っているか?

- 回答: 大枠は正しいが1点訂正が必要。`record`であっても、複数回`new`すれば作られるオブジェクトはメモリ上**別々のインスタンスのまま**(ここは変わらない)。変わるのは「別インスタンスでも、中身が同じなら`equals()`で"等しい"と判定される」という点。「同一インスタンスになる」のではなく、「別インスタンスだけど、Setから見たら等価(同じものとみなす)」という状態。

  ```
  Improper: インスタンスA ≠ インスタンスB (別物として扱われる) → 両方入る
  Proper  : インスタンスA ≠ インスタンスB (実体は別物のまま)
            しかし A.equals(B) == true (中身が同じだから)
            → HashSetは「これは重複だ」と判断してBを弾く
  ```

  正確には「`record`は、別インスタンスであっても中身の比較で重複を正しく検出できる`equals()`/`hashCode()`を自動生成してくれるので、`Set`が本来期待している『重複を許さない』という役割をちゃんと果たせる」という理解が正しい。
