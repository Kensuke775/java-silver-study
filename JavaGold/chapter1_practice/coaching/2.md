# Chapter1 コーチング記録

## 2. ジェネリクス (2.1〜2.8) 要約

### 2.1 非ジェネリッククラス

**教科書の例(`chap1/3`):**

```java
// Box.java
 1  public class Box {
 2      private Object obj;
 3      public void set(Object obj) { this.obj = obj; }
 4      public Object get() { return obj; }
 5  }
```

```java
// Main.java
 1  public class Main {
 2      public static void main(String[] args) {
 3          Box box = new Box();
 4          box.set("Java");
 5          String s = (String) box.get();   // 5行目
 6          box.set(10);
 7       // s = (String) box.get();          // 7行目コメントアウト
 8      }
 9  }
```

**説明したポイント**

- ジェネリクス以前の発想では、「どんな型でも入れられる箱」を作りたいとき`Object`型で受ける。
- 5行目: `"Java"`を入れて取り出す分には、`get()`の戻り値`Object`を`(String)`にダウンキャストすれば問題なく動く。
- 6行目で`box.set(10)`とすると、内部の`obj`は`Integer`オブジェクトに上書きされる。
- もし7行目のコメントを外して`(String) box.get()`を実行すると、実体は`Integer`なのに`String`へキャストしようとするため、**コンパイルは通るが実行時に`ClassCastException`がスローされる**。

**セクションの核心**

`Box`クラス自体は「文字列だけを入れてほしい」という意図があっても、`Object`で受けている限りコンパイラはそれを一切保証してくれない。不整合は**実行時になって初めて**発覚する。これがジェネリクス導入前の弱点であり、2.2以降で学ぶ「型パラメータ`<T>`」がこの問題を解決する動機になっている。

**疑問**:

- 質問: オブジェクトに入れて取り出す(get)と、中に入ってるのがJavaじゃなくなるんですか?それともsetで上書きできるってこと?
- 回答: `set()`で上書きされる。`Box`は`obj`フィールドを1つだけ持つので、`set()`を呼ぶたびにその参照がまるごと書き換わる。
  ```
  box.set("Java")  →  box.obj ─→ "Java"
  String s = ... 取り出す  →  s ─→ "Java" (boxとは別に独立して持つ)

  box.set(10)      →  box.obj ─→ Integer(10)   ("Java"への参照はboxから消える)
                       s は変わらず "Java" のまま(sは既に取り出し済みだから)
  ```
  つまり`box`の中に「Javaも10も両方入っている」わけではなく、後から`set()`した値で完全に置き換わる(変数への再代入と同じイメージ)。`s`には`set(10)`より前に取り出しておいた`"Java"`が別に保存されているので、`s`自体は`"Java"`のままだが、それは`box`の中身とは無関係な、既に取り出し済みの独立した参照。7行目のコメントを外すと、その時点で`box.get()`は`Integer`を指しているため`(String)`キャストで`ClassCastException`になる。









### 2.2 ジェネリッククラス/インタフェースの宣言

専用の`sample/chap1/N`ディレクトリはなく、教科書内のインライン例(図1-1)で説明されている。

**宣言の構文**

```java
1  class Foo<T> {}
2  interface Bar<T, R> {}
```

**教科書の図1-1の例**

```java
// Foo
1  class Foo<T> {
2      private T obj;
3      public Foo(T obj) { this.obj = obj; }
4      public T get() { return obj; }
5  }
```

```java
// Baz
1  class Baz<E> {
2      private E e1 = new E();          // ① コンパイルエラー
3      private static E e2;             // ② コンパイルエラー
4      private static E errMethod(E e3) {
5          return e3;                   // ② コンパイルエラー
6      }
7  }
```

```java
// Bar
1  interface Bar<T, R> {
2      public R method(T t);
3  }
```

**説明したポイント**

- `Foo<T>`の型パラメータ`T`は、コンストラクタの引数(2行目)、フィールド(2行目)、メソッドの戻り値(4行目)など、非staticなメンバ全体がスコープ。
- `Bar<T, R>`のように複数の型パラメータを持てる。`T`は引数、`R`は戻り値というように使い分け可能。
- ①`new E()`はコンパイルエラー: 型パラメータに実際どの型が入るか分からないため、型パラメータを使ったインスタンス化はできない。
- ②`private static E e2;` / `static E errMethod(E e3)`もコンパイルエラー: 型パラメータは非staticなので、staticコンテキスト(staticフィールド/staticメソッド)からはアクセスできない。

**参考: 型パラメータの命名慣習**

| 記号 | 用途 |
|---|---|
| `E` | コレクションの要素 |
| `K` | マップのキー |
| `V` | マップの値 |
| `T` | 一般的な型 |

**セクションの核心**

型パラメータは「そのクラスのインスタンスが生成されるときに初めて具体的な型が決まる」プレースホルダーであり、インスタンスに紐づく情報。static文脈はインスタンス生成前・インスタンスに依存しないコンテキストなので、型パラメータとは原理的に相性が悪い(2.5で学ぶ「staticなジェネリック**メソッド**」との対比が重要)。

**疑問**:

- 質問: staticメソッドが使えないのは、独立したメソッドはジェネリクスに合わないってこと?
- 回答: その理解で合っている。型パラメータは「インスタンスが生成される瞬間に初めて具体的な型が決まる」もの。static文脈はインスタンスに依存せず、クラスに1つだけ存在し、インスタンスが1つも作られていなくても呼び出せる。つまり「どのインスタンスのTなのか」という紐付け先が存在しないため、型パラメータを使いようがない。

- 質問: Baz例でprivate/publicを使っているのは、Genericsの習わし・カプセル化のようなものか?
- 回答: Genericsとは無関係の、普通のJavaのカプセル化の作法。フィールドを`private`にして直接アクセスさせず、`public`なgetter/setter経由でアクセスさせるという一般的なOOPのベストプラクティスをたまたまこの例でも使っているだけで、Genericsだから特別にそうする、というルールはない。

- 質問: 型パラメータって何?
- 回答: `<T>`のように宣言される「型のための変数(プレースホルダー)」。普通の変数(`int x`)は後で具体的な値が入るのに対し、型パラメータ(`class Foo<T>`)は後で具体的な型(`String`, `Integer`など)が入る。`Foo<String>`とインスタンス化した瞬間、そのインスタンス内では`T`が`String`に置き換わったものとしてコンパイラが扱う。`new E()`がエラーになるのは、コンパイル時点で`E`が単なるプレースホルダーでしかなく、具体的な型がまだ決まっていないため実体化できないから。

### 2.3 ジェネリクスの使用

**教科書の例(`chap1/4`):**

```java
// Box.java
 1  class Box<T> {
 2      private T obj;
 3      public void set(T obj) { this.obj = obj; }
 4      public T get() { return obj; }
 5  }
```

```java
// Main.java
 1  public class Main {
 2      public static void main(String[] args) {
 3          Box<String> box1 = new Box<String>();
 4          box1.set("Gold");
 5          String s = box1.get();
 6       // box1.set(10);                     // 6行目コンパイルエラー
 7          Box<Integer> box2 = new Box<Integer>();
 8          box2.set(10);
 9          Integer i = box2.get();
10       // Box<int> box3 = new Box<int>();   // 10行目コンパイルエラー
11          Box box4 = new Box();
12          box4.set(true);
13          Boolean b = (Boolean) box4.get();
14      }
15  }
```

**説明したポイント**

- 3行目: 型パラメータに`String`を指定してインスタンス化。`box1`は`String`専用の箱になる。
- 4〜5行目: `set()`で`"Gold"`を設定し、`get()`はキャストなしで`String`型変数`s`に代入できる(2.1の`Object`版との最大の違い)。
- 6行目: `box1`は`String`専用なので`Integer`は入れられない → コンパイルエラー(2.1では`ClassCastException`だったのが、ここではコンパイル時にブロックされる)。
- 7〜9行目: 同様に`Integer`専用の`box2`を生成。
- 10行目: 型パラメータには基本データ型(`int`)を指定できない。ラッパークラス`Integer`にする必要がある。
- 11〜13行目: 型パラメータを省略した**raw型**。内部的には`Object`扱いになるため、2.1の`Box`と同じく取得時にキャストが必要(`(Boolean)`)。raw型はJava 5以前との後方互換のために許可されているだけ。

**コンパイル結果**

```
ノート : Main.javaの操作は、未チェックまたは安全ではありません。
ノート : 詳細は、-Xlint:uncheckedオプションを指定して再コンパイルしてください。
```

raw型(11〜13行目)を使うとコンパイル自体は成功するが、この警告が出る。`javac -Xlint:unchecked Main.java`で詳細(`set(T)`への無検査呼出し、など)を確認できる。

**セクションの核心**

ジェネリッククラスをパラメータ化した型(`Box<String>`など)で使うと、2.1で見た「実行時までエラーが分からない」問題が**コンパイル時のチェック**に置き換わる。ただしraw型として使うと、この恩恵は失われ2.1と同じ挙動(取得時にキャスト必須・型不整合は実行時発覚)に戻ってしまう。raw型は「ジェネリクスの安全網から抜け出す抜け穴」と捉えると理解しやすい。

**疑問**:

- 質問: 6行目と10行目、それぞれなぜコンパイルエラーになるのか?
- 回答(ユーザーの解答): 6行目は`box1`が`new Box<String>()`で作られているため`T`が`String`に書き換わっており、`set()`に渡した中身がintなので型エラーになる。10行目は、型パラメータには基本的にラッパークラスしか受け付けないため、プリミティブ型の基本データ型を指定することはできない。
- 補足: どちらも正しい。6行目はより正確には「`set()`の引数型が`String`に固定されているのに、渡している実引数が`String`型ではない(int/Integerとの間に代入互換性がない)ため」の型不一致。10行目は型パラメータに指定できるのは参照型のみで、`int`のような基本データ型は指定できないため、対応するラッパークラス(`Integer`)を使う必要がある、という理解で正確。

### 2.4 ダイヤモンド演算子

**教科書の例(`chap1/5`):** `Box`クラスは`chap1/4`と同じ(`class Box<T> { ... }`)。

```java
// Main.java
 1  public class Main {
 2      public static void main(String[] args) {
 3          Box<Integer> iBox = new Box<>();
 4       // Box<> err = new Box()<String>;      // 4行目コンパイルエラー
 5          method(new Box<>());
 6          Box<String> sBox = method();
 7      }
 8      public static void method(Box<String> box) { /* 処理 */ }
 9      public static Box<String> method() {
10          return new Box<>();
11      }
12  }
```

**説明したポイント**

- 3行目: 左辺`Box<Integer>`から型推論されるため、右辺の型パラメータ指定を`<>`に省略できる。
- 4行目: 変数宣言側に`<>`を書くことはできない。省略できるのはインスタンス生成側の`<>`だけ。
- 5、8行目: `method()`の仮引数が`Box<String>`で宣言されているため、実引数側`new Box<>()`は型推論可能。
- 6、9〜11行目: `method()`の戻り値の型が`Box<String>`なので、その中の`new Box<>()`(10行目)も型推論できる。ただし呼び出し側の6行目(変数宣言)では型パラメータの指定を省略できない。

**セクションの核心**

ダイヤモンド演算子`<>`が省略できるのは常にインスタンス生成側で、コンパイラが型を推論できる文脈がある場合のみ(変数宣言・メソッドの仮引数/戻り値など)。「宣言側」と「生成側」という軸で覚えると、4行目のようなエラーを判断しやすい。

**疑問**:

- 質問(2.3の`Box<Boolean> box4 = new Box<Boolean>();`について): 左と右、両方に`Box<Boolean>`ってわざわざ書いてる感じ?
- 回答: その通り。左辺は変数`box4`の宣言型、右辺は`new`で実際に生成するオブジェクトの型で、構文上は別々に書く必要がある。これが冗長だという点を解消するのがまさにこのダイヤモンド演算子(`Box<Boolean> box4 = new Box<>();`のように右辺を省略できる)。

- 質問: メソッドにBoxの型を使う(引数や戻り値に`Box<T>`を指定する)、というのが全然イメージできない。
- 回答: `Box<T>`はただの「型」なので、`int`や`String`と同じ感覚でメソッドの引数・戻り値の型として指定できる、というのがポイント。

  ```java
   1  public class Main {
   2      public static void main(String[] args) {
   3          Box<Integer> myBox = new Box<>();
   4          myBox.set(10);
   5
   6          printBoxContent(myBox);        // myBoxをメソッドに渡す
   7
   8          Box<Integer> anotherBox = createBox();  // メソッドからBoxを受け取る
   9      }
  10
  11      // 引数としてBox<Integer>を受け取るメソッド
  12      static void printBoxContent(Box<Integer> box) {
  13          System.out.println(box.get());
  14      }
  15
  16      // 戻り値としてBox<Integer>を返すメソッド
  17      static Box<Integer> createBox() {
  18          Box<Integer> box = new Box<>();
  19          box.set(100);
  20          return box;
  21      }
  22  }
  ```

  6行目は`myBox`という箱を`printBoxContent`メソッドに丸ごと渡し、メソッド側(12行目)は`Box<Integer> box`という引数でその箱を受け取り中身を取り出して使う。8行目は`createBox()`メソッドが新しい箱を作って中身を入れてから箱ごと返している。`int`や`String`のような値をメソッド間で受け渡しするのと同じ感覚で、「箱(Box)」というオブジェクト自体を丸ごと受け渡ししているだけ、というイメージ。教科書2.4の`method(Box<String> box)` / `Box<String> method()`もこのパターン。

### 2.5 ジェネリックメソッド

**教科書の例(`chap1/6`、抜粋):**

```java
// Main.java
 4  class Main {
 5      <T> List<T> foo() {
 6          return new ArrayList<T>();
 7      }
 8      static <E> void bar(List<E> list) {
 9          for (E e : list) System.out.println(e);
10      }
11
12      public static void main(String[] args) {
13          Main obj = new Main();
14          List<Integer> list1 = obj.foo();
15          List<Integer> list2 = obj.<Integer>foo();
16          list1.add(10);
17          list2.add(20);
18          Main.bar(list1);
19          Main.<Integer>bar(list2);
20      }
21  }
```

**説明したポイント**

- クラス自体は`Main<T>`のようにジェネリック宣言されていなくても、`foo()`・`bar()`のようにメソッド単位で型パラメータ`<T>`, `<E>`を持てる。
- 構文上、型パラメータリストは戻り値の型の直前に書く(5行目: `<T> List<T> foo()`)。
- 14行目: `List<Integer> list1 = obj.foo();` — 代入先の型`List<Integer>`から、`foo()`の`T`が`Integer`だとコンパイラが推論するため、具体的な型指定を省略して呼び出せる。
- 15行目: 型指定を省略しない場合は、呼び出すメソッド名の直前に`.<Integer>`のように明示する。
- 8行目: `bar()`は**staticなジェネリックメソッド**。2.2で見た「staticコンテキストではクラスの型パラメータは使えない」という制約とは違い、**メソッド自身が持つ型パラメータはstaticでも問題なく使える**。
- 18〜19行目: `bar()`の呼び出し。実引数`list1`の型から`E`が`Integer`と推論される(18行目)か、明示的に指定する(19行目)かのどちらか。

**ポイント(教科書内コラム): staticなジェネリックメソッド**

ジェネリッククラスの型パラメータとジェネリックメソッドの型パラメータは別物。前者はstaticメンバには使えないが、後者(メソッド自身の型パラメータ)はstaticメソッドでも使用可能。

**セクションの核心**

型パラメータは「クラスに属する」か「メソッドに属する」かの2種類がある、と整理すると2.2との対比が理解しやすい。クラスの型パラメータはインスタンス生成時に決まる(→staticとは相性が悪い)一方、メソッドの型パラメータは、そのメソッドが呼び出されるたびに独立して決まるため、staticかどうかに関係なく使える。

**疑問**:

- 質問: 2.2のBazでは`E`がstaticで使えないのに、なぜこの`Main`の`bar()`ではstaticなのに`E`を使えるのか?クラスに`<E>`が付いていないのに、中のstaticメソッドで`E`を使えるのがイメージつかない。
- 回答: 「フィールド vs ローカル変数」の類推で考えると分かりやすい。

  ```java
   1  class Sample {
   2      int x = 10;              // インスタンスフィールド
   3
   4      void instanceMethod() {
   5          System.out.println(x);   // OK: インスタンスに紐づくxにアクセスできる
   6      }
   7
   8      static void staticMethod() {
   9          System.out.println(x);   // NG: staticからインスタンスフィールドxは見えない
  10          int x = 5;                // OK: これはstaticメソッド自身のローカル変数x(別物)
  11          System.out.println(x);   // これは今作ったローカルのx(5)
  12      }
  13  }
  ```

  9行目がエラーになるのは「インスタンスに属するx」をインスタンスなしで参照しようとしているから。しかし10行目のように、staticメソッドが自分だけのローカル変数xを新しく作るのは何の問題もない。名前が同じ`x`なだけで、2行目のフィールドとは完全に別物。

  型パラメータも全く同じ構造:
  - `Baz<E>`の`E`は「インスタンスが生成されたときに決まる」もの → フィールドと同じ立場 → staticからは触れない。
  - `Main`クラス自体には型パラメータがない。`bar()`の`<E>`は、`bar()`が呼ばれるたびに新しく用意される「メソッド専用の入れ物」で、ローカル変数と同じようにそのメソッドの中でだけ生きて完結する。だからクラスがstaticかインスタンスか、という話と一切関係なく使える。

  まとめ: 「クラスの型パラメータ」=フィールド的な存在(インスタンス依存)、「メソッドの型パラメータ」=ローカル変数的な存在(呼び出しごとに独立)、という対応で覚えるとstatic可否の判断がブレなくなる。

- 質問: `foo()`は戻り値が`List<T>`で`<T>`が付いているが、`bar()`は戻り値が`void`なのに`<E>`が付いているのはなぜ?型パラメータと戻り値の型を混同していないか確認したい。
- 回答: `<T>`/`<E>`(型パラメータリスト)と戻り値の型は別物。構文は`[修飾子] <型パラメータリスト> 戻り値の型 メソッド名(引数リスト)`で固定されており、型パラメータリストは戻り値が何であってもその直前に置かれる。`foo()`は戻り値`List<T>`の前に`<T>`、`bar()`は戻り値`void`の前に`<E>`が付いているだけで、どちらも同じ構文規則に従っている。

- 質問: 型パラメータリストの位置(戻り値の型の直前)は絶対に前後できないのか?
- 回答: 前後できない。`static void bar<E>(List<E> list)`のように戻り値の型の後ろに書くと実際にコンパイルエラーになることを`javac`で確認済み(`'('がありません` / `型の開始が不正です`)。JLSのメソッド宣言構文で位置が固定されているため。

- 質問: 修飾子なしで別クラスのstaticメソッドを直接呼べるのはどの範囲までか?同じパッケージなら大丈夫?
- 回答: 「同じパッケージなら見える」は誤り。修飾子なしで呼べるのは**そのクラス自身、またはスーパークラス/実装インタフェースから継承したメンバーだけ**。同じパッケージの無関係な別クラスのstaticメソッドは、修飾子(クラス名)なしでは呼べない。`javac`で実際に検証済み:
  ```java
  // Helper.java (デフォルトパッケージ)
  public class Helper {
      static void bar() { System.out.println("bar called"); }
  }
  // Caller.java (同じデフォルトパッケージ)
  public class Caller {
      public static void main(String[] args) {
          bar();   // エラー: シンボルを見つけられません
      }
  }
  ```
  一方、継承関係があれば修飾子なしで呼べる:
  ```java
  public class Parent { static void bar() { System.out.println("bar from Parent"); } }
  public class Child extends Parent {
      public static void main(String[] args) { bar(); }   // OK: "bar from Parent"
  }
  ```
  呼び出す方法は結局3通り: ①同じクラス内(または継承元)に定義する ②`クラス名.method()`と修飾する ③`import static`する。

**まとめ: ジェネリックメソッドの4つの呼び出し方(`<Integer>bar(list)`が構文エラーになる理由)**

型引数を明示的に書きたいなら、必ず修飾子込みの形にしなければならない。`Main.<Integer>bar(list)`のように、クラス名(または`this`)+`.`+`<型引数>`+メソッド名、という形しか文法上許されない。

ただし、そもそも型引数を明示的に書く必要自体がないことが多い。`Main.bar(list1);`のように修飾子だけ付けて型引数は省略しても、引数`list`の型(`List<Integer>`)から`E`は自動的に`Integer`だと推論される。整理すると呼び出し方は次の4パターンで、「修飾子なし+型引数あり」という組み合わせだけが存在しない:

| 書き方 | 型引数 | 修飾子 | 可否 |
|---|---|---|---|
| `bar(list);` | 省略(推論) | なし | OK(同じクラス内から) |
| `Main.bar(list);` | 省略(推論) | あり | OK |
| `Main.<Integer>bar(list);` | 明示 | あり | OK(冗長だが有効) |
| `<Integer>bar(list);` | 明示 | なし | **構文エラー** |

型の種類とは無関係の一般ルール(`<String>bar(list)`のように型を変えても同じく構文エラーになることを検証済み)。「型引数を書く=修飾子必須」というより、「型引数を明示的に書きたい場合に限り、修飾子とセットでなければならない」が正確。普段は型推論に任せて型引数自体を省略するのが一般的。

(→ 実践: chapter1_practice/problems_v1.md 問題6-2)

### 2.6 境界付き型パラメータ (`extends`)

- `class Foo<T extends Number> {}` で、Tに指定できる型をNumberおよびそのサブタイプに制限。
- インタフェースを境界にする場合も`extends`を使う(`implements`ではない)。例: `<T extends Comparable<T>>`。
- 境界を付けると、その境界の型が持つメソッド(例: `compareTo()`)を型パラメータ経由で呼び出せるようになる。
- `<T, X extends T>` のように、先に宣言した型パラメータを後続の境界に使うことも可能。
- 境界なしの`<T>`ではObjectクラスのメソッドしか呼べない(`==`や`<`のような基本データ型演算子はもちろん不可)。

### 2.7 非境界ワイルドカード型 (`<?>`)

- 配列は共変(`Number[] nArr = iArr;`が可能)だが、実行時に`ArrayStoreException`のリスクがある。
- ジェネリクスは**不変**: `List<Number>`と`List<Integer>`は無関係の型。`List<Number> nList = ...; List<Integer> iList = ...; nList = iList;`はコンパイルエラー。
- `List<?>`を使うと「何らかの型のList」を受け取れるようになる(メソッド引数などで汎用的に扱いたいとき)。
- **非対称ルールが最重要**: `List<?>`は要素の**追加はnullのみ可**(具体的な型が不明なため安全性を保てない)、**取得はObject型**になる。
- ワイルドカードは「型パラメータを宣言する場所」には使えない。`class Box<?> {}`や`new ArrayList<?>()`はエラー。使えるのはあくまで変数/引数の型として指定する側だけ。

### 2.8 境界付きワイルドカード型 (PECS)

- 上限境界 `<? extends T>`: Tまたはそのサブタイプ。**取得(get)は安全、追加(add)はnullのみ**(Producer=extendsはget専用、と覚える)。
- 下限境界 `<? super T>`: Tまたはそのスーパータイプ。**追加(add)はTの型まで安全、取得(get)はObject型**(Consumer=superはadd専用、と覚える)。
- 通称 **PECS (Producer Extends, Consumer Super)**。「取り出す(読む)用途ならextends、詰め込む(書く)用途ならsuper」。
- 表1-2の対応(教科書内):


| 構文              | 要素の追加(add) | 要素の取得(get) |
| --------------- | ---------- | ---------- |
| `<?>`           | nullのみ     | Object型    |
| `<? extends T>` | nullのみ     | T型         |
| `<? super T>`   | T型まで       | Object型    |

**メモ(並行して進めている出題セッションの例題より)**: 教科書は`List<T>`での説明だったが、`Box<T>`のような自作の任意のジェネリッククラスでも全く同じ理屈が成り立つ。

- `Box<? extends Number>` — 「Numberか、その何らかのサブタイプ」
  - 実際の型は`Box<Integer>`かもしれないし`Box<Double>`かもしれない。コンパイラにはどのサブタイプか分からない。
  - `get()`は安全: 中身が何であれ、少なくとも`Number`ではあることが保証されているので、`Number n = box.get();`はOK。
  - `set()`は基本的に不可: もし実際は`Box<Double>`なのに`box.set(10)`(Integerを入れる)を許してしまうと、型の整合性が壊れる。コンパイラは「実際の型が何か分からない」ので、安全側に倒してnull以外の`set()`を一切禁止する。
  - まとめ: 「取り出すのは安全、入れるのはほぼ不可能」→ 読み取り専用として使う場面向け。

- `Box<? super Integer>` — 「Integerか、その何らかのスーパータイプ」
  - 実際の型は`Box<Integer>`かもしれないし`Box<Number>`、`Box<Object>`かもしれない。
  - `set()`は安全: `Integer`(またはそのサブタイプ)を入れる分には、相手がInteger/Number/Objectのどれであっても必ず受け入れられるので、`box.set(10)`はOK。
  - `get()`はObjectとしてしか受け取れない: 実際の型がどこまで上位か分からないので、コンパイラは「少なくともObjectではある」としか保証できない。`Number n = box.get();`のようにObjectより具体的な型に代入しようとするとコンパイルエラーになる(`Object o = box.get();`ならOK)。
  - まとめ: 「入れるのは安全、取り出すのはObjectとしてのみ」→ 書き込み専用として使う場面向け。

## この単元でよくある引っかけパターン(自己チェック用ヒント)

次の観点を自分の言葉で説明できるか確認してみてください。答え合わせはせず、まず自分で考えること。

1. **raw型を経由すると何が起きるか？** — `Box box = new Box(); box.set(10);` は型的に何が保証されなくなる？コンパイルは通る？警告は出る？
2. **static文脈と型パラメータ** — クラスの型パラメータ`T`をstaticフィールドやstaticメソッドの引数に直接使えないのはなぜ？一方でstaticなジェネリックメソッド`<E> static void bar(...)`はなぜ許されるのか、両者の違いを説明できるか。
3. **配列とジェネリクスの共変性の違い** — `Number[] arr = new Integer[3];`はコンパイルが通るのに、`List<Number> list = new ArrayList<Integer>();`はなぜコンパイルエラーになるのか。実行時エラーのリスクの所在がどう違うか。
4. `**List<?>`に`add(null)`だけが許される理由** — nullがなぜ唯一の例外なのか、型安全性の観点から説明できるか。
5. **PECSの根拠** — `<? extends Number>`でaddができない理由と、`<? super Number>`でgetがObject型になる理由を、それぞれ「コンパイラが具体的に何を知らないか」から説明できるか。
6. **ダイヤモンド演算子の省略可否** — 省略できる場所とできない場所を、宣言側/生成側という軸で言い分けられるか。
