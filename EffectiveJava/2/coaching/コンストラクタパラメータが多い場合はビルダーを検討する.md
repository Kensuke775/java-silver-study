# Chapter2 コーチング記録

## Item 2: Consider a builder when faced with many constructor parameters(コンストラクタパラメータが多い場合はビルダーを検討する)

**教科書の例(問題設定):** 必須項目3つ+任意項目20個以上を持つ「栄養成分表示」クラスをどう作るか。

  


**パターン1: テレスコーピングコンストラクタパターン(良くない例)**

```java
1  public class NutritionFacts {
2      private final int servingSize;  // 必須
3      private final int servings;      // 必須
4      private final int calories;      // 任意
5      private final int fat;           // 任意
6      private final int sodium;        // 任意
7      private final int carbohydrate;  // 任意
8
9      public NutritionFacts(int servingSize, int servings) {
10         this(servingSize, servings, 0);
11     }
12     public NutritionFacts(int servingSize, int servings, int calories) {
13         this(servingSize, servings, calories, 0);
14     }
15     public NutritionFacts(int servingSize, int servings, int calories, int fat) {
16         this(servingSize, servings, calories, fat, 0);
17     }
18     // ... 全パラメータを取るコンストラクタまで続く
19 }
20
21 NutritionFacts cocaCola = new NutritionFacts(240, 8, 100, 0, 35, 27);
```

- 必須パラメータ+任意パラメータの組み合わせごとにコンストラクタを増やしていく方式。
- 21行目: 使いたくない任意パラメータにも`0`のような値を渡す必要があり、どの引数が何を意味するか読み取りにくい。パラメータの並び順を間違えても**コンパイルエラーにならず実行時に不具合になる**(Item51)。

  


**パターン2: JavaBeansパターン(良くない例)**

```java
1  public class NutritionFacts {
2      private int servingSize = -1;  // 必須(デフォルトなし)
3      private int servings     = -1;  // 必須(デフォルトなし)
4      private int calories     = 0;
5      // ...
6
7      public NutritionFacts() { }
8      public void setServingSize(int val) { servingSize = val; }
9      public void setServings(int val)     { servings = val; }
10     // ...
11 }
12
13 NutritionFacts cocaCola = new NutritionFacts();
14 cocaCola.setServingSize(240);
15 cocaCola.setServings(8);
16 cocaCola.setCalories(100);
```

- 引数なしコンストラクタで作ってから、setterで1つずつ値を設定する方式。読みやすいが、以下の欠陥がある。
  - **一貫性のない状態が作れてしまう**: 13〜14行目の間は`servings`が未設定のまま。この状態でオブジェクトを使うと、バグの原因箇所から離れたところで失敗が起き、デバッグが困難になる。
  - **不変クラス(Item17)にできない**: setterで後から値を変えられる前提のため。
  - スレッドセーフにするための追加対応が必要になる。

  


**パターン3: Builderパターン(推奨)**

```java
1  public class NutritionFacts {
2      private final int servingSize;
3      private final int servings;
4      private final int calories;
5      private final int fat;
6      private final int sodium;
7      private final int carbohydrate;
8
9      public static class Builder {
10         // 必須パラメータ
11         private final int servingSize;
12         private final int servings;
13
14         // 任意パラメータ(デフォルト値で初期化)
15         private int calories      = 0;
16         private int fat           = 0;
17         private int sodium        = 0;
18         private int carbohydrate  = 0;
19
20         public Builder(int servingSize, int servings) {
21             this.servingSize = servingSize;
22             this.servings    = servings;
23         }
24
25         public Builder calories(int val)     { calories = val;     return this; }
26         public Builder fat(int val)          { fat = val;          return this; }
27         public Builder sodium(int val)       { sodium = val;       return this; }
28         public Builder carbohydrate(int val) { carbohydrate = val; return this; }
29
30         public NutritionFacts build() {
31             return new NutritionFacts(this);
32         }
33     }
34
35     private NutritionFacts(Builder builder) {
36         servingSize  = builder.servingSize;
37         servings     = builder.servings;
38         calories     = builder.calories;
39         fat          = builder.fat;
40         sodium       = builder.sodium;
41         carbohydrate = builder.carbohydrate;
42     }
43 }
44
45 NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8)
46         .calories(100).sodium(35).carbohydrate(27).build();
```

**説明したポイント**

- 9行目: `Builder`は`NutritionFacts`の**staticメンバクラス**(Item24)として内側に定義する。
- 20〜23行目: `Builder`のコンストラクタは必須パラメータだけを受け取る。
- 25〜28行目: 任意パラメータ用のメソッドは、値を設定した後に`return this;`で**自分自身(Builderインスタンス)を返す**。これによって45〜46行目のように`.calories(100).sodium(35)...`とメソッドを鎖のようにつなげて書ける(**メソッドチェーン**、**fluent API**)。
- 30〜32行目: 最後に引数なしの`build()`を呼ぶと、そこで初めて本体の`NutritionFacts`インスタンスが作られる。
- 35〜42行目: 本体側のコンストラクタは`private`で、`Builder`からしか呼ばれない。`Builder`が持っていた値をコピーして、最終的に**全フィールドが**`final`**の不変オブジェクト**として完成する。

**このパターンの利点**

- テレスコーピングコンストラクタの欠点(読みにくさ・パラメータ順ミスのリスク)がない。
- JavaBeansパターンの欠点(構築途中の不整合な状態、可変性の強制)もない。**構築が全て終わった**`build()`**の瞬間に初めて本体のインスタンスが生成される**ため、常に完成した一貫性のある状態でしか`NutritionFacts`は存在しない。
- 各パラメータのデフォルト値が`Builder`の1箇所にまとまる。

  


**階層(継承)へのBuilder適用: Pizzaの例**

```java
1  public abstract class Pizza {
2      public enum Topping { HAM, MUSHROOM, ONION, PEPPER, SAUSAGE }
3      final Set<Topping> toppings;
4
5      abstract static class Builder<T extends Builder<T>> {
6          EnumSet<Topping> toppings = EnumSet.noneOf(Topping.class);
7
8          public T addTopping(Topping topping) {
9              toppings.add(Objects.requireNonNull(topping));
10             return self();
11         }
12
13         abstract Pizza build();
14
15         // サブクラスは必ずこれをオーバーライドし"this"を返す
16         protected abstract T self();
17     }
18
19     Pizza(Builder<?> builder) {
20         toppings = builder.toppings.clone();
21     }
22 }
```

```java
1  public class NyPizza extends Pizza {
2      public enum Size { SMALL, MEDIUM, LARGE }
3      private final Size size;
4
5      public static class Builder extends Pizza.Builder<Builder> {
6          private final Size size;
7
8          public Builder(Size size) {
9              this.size = Objects.requireNonNull(size);
10         }
11
12         @Override public NyPizza build() {
13             return new NyPizza(this);
14         }
15
16         @Override protected Builder self() { return this; }
17     }
18
19     private NyPizza(Builder builder) {
20         super(builder);
21         size = builder.size;
22     }
23 }
```

```java
1  NyPizza pizza = new NyPizza.Builder(SMALL)
2          .addTopping(SAUSAGE).addTopping(ONION).build();
```

**説明したポイント**

- `Pizza.Builder<T extends Builder<T>>`は**再帰的な型パラメータ**(Item30)。抽象メソッド`self()`とセットで使うことで、`NyPizza.Builder`のようなサブクラス側でも、親クラス由来の`addTopping(...)`を呼んだ戻り値がキャスト不要で`NyPizza.Builder`型のまま連鎖できる。この仕組みは「シミュレートされたself型イディオム」と呼ばれる(Javaには`self`型という言語機能自体が存在しないための回避策)。
- `NyPizza.Builder`の`build()`は、親の`Pizza.Builder`が宣言する`Pizza`型ではなく、より具体的な`NyPizza`型を返す。この「サブクラスのメソッドが、親で宣言された戻り値型のサブタイプを返す」ことを**共変戻り値型**と呼ぶ。これにより呼び出し側はキャストなしで使える。

  


**Builderパターンの欠点**

- オブジェクトを作る前に、必ず`Builder`を先に作る必要があるため、性能がシビアな場面ではオーバーヘッドになりうる。
- テレスコーピングコンストラクタより記述量が多くなる。**パラメータが4個以上**になるくらいから使う価値が出てくる、という目安。
- 将来パラメータが増える可能性も考えると、最初からBuilderで作っておいた方が、後からコンストラクタ/staticファクトリから移行するより変更コストが低い。

  


**セクションの核心**

コンストラクタやstaticファクトリのパラメータが多く(特に4個以上)、任意パラメータや同じ型が並びやすい場合はBuilderパターンが向いている。テレスコーピングコンストラクタより読み書きしやすく、JavaBeansパターンより安全(常に一貫した状態のオブジェクトしか存在しない)。

## 疑問

<br>

**Q. 実際に使う場合、フロントエンドで入力していくイメージ?パターン1は任意項目にも0を入れなきゃいけない、パターン2はsetterを毎回1個ずつ呼ばなきゃいけない、パターン1は全パターン分書かなきゃいけないし後で見返すのも大変、ということ?**

その理解で正しい。パターン1(テレスコーピング)は、使わない任意パラメータにもダミー値を渡す必要があり、コンストラクタ自体を組み合わせ分だけ定義しなければならず、呼び出し側も`new NutritionFacts(240, 8, 100, 0, 35, 27)`のようにどの数字が何かを引数の位置で数えないと分からない。パターン2(JavaBeans)は`setServingSize(240)`のようにsetterを1メソッドずつ呼ぶ必要がある。実務ではWebフォームで必須+大量の任意項目を入力させ、送信データからオブジェクトを作る場面がまさにこの状況に当たる。

<br>

**Q. JavaBeansパターンは、フロントエンドで1行ずつEnter確定していかないとDB保存できない、一時保存的なもの?setterを毎回呼ばなきゃいけないってことは、まとめて処理できないということ?**

誤解。setterを1つずつ呼ぶのはJavaのコード内部の話であり、フロントエンドのユーザー操作(1行ずつ確定)とは無関係。ユーザーが1回の送信操作で全データを送っても、サーバー側コードは`n.setServingSize(...); n.setServings(...); ...`と1行ずつ、ミリ秒未満の間に連続実行される。「まとめて処理できない」のではなく、まとめて(1つのメソッド内で連続して)処理していても、その一瞬の間に中途半端な状態が存在してしまう、というのが問題。

<br>

**Q. setCalories等はまとめて処理できるはずなのに、なぜ中途半端な状態のオブジェクトが存在しうるのか?**

コンピュータのプログラムは(見た目が一括でも)必ず1行ずつ順番に実行されるから。複数の文を同時に実行することはできず、必ずT1→T2→T3→T4という別々の瞬間が(ナノ秒単位でも)存在する。その各瞬間、オブジェクトは実際にメモリ上に存在していて、まだ全部の値がセットされていない中途半端な状態のままそこにいる。普段は誰も気にしないが、(1)途中で例外が起きて未完成のまま外に渡ってしまう場合、(2)他のスレッドがちょうどその中間状態を読み取ってしまう場合、に問題化する。

<br>

**Q. パターン1と2の良いところを組み合わせたのがBuilderで、途中で例外が起きても1行で済ませられるから入力できなかった部分ができるバグを防げる、保守性が高いということ?**

大枠は正しいが1点訂正。「1行で済ませる」のではなく、`Builder`自体はJavaBeansと同じく`.calories(100).sodium(35)...`と1ステップずつ組み立てられるので、Builder自身にも中途半端な状態は普通に存在する。本当の違いは「中途半端な状態がどこに存在するか」。パターン2は本体の`NutritionFacts`自身に中途半端な状態が存在してしまうが、Builderでは中途半端な状態は使い捨ての`Builder`オブジェクトの中にだけ存在し、本体の`NutritionFacts`は`build()`が呼ばれた1行(コンストラクタ呼び出し)で初めて・一気に完成した状態として生成される。途中で何が起きても影響を受けるのは使い捨てのBuilderだけで、他のコードが未完成品を誤って使い回す事故が構造的に起きない。「途中経過をなくした」のではなく「途中経過を、本体とは無関係な仮の場所(Builder)に隔離した」という発想。

<br>

**Q. `return new NutritionFacts(this);`のthisは、中のインスタンスを全て返してるということ?**

「全て返している」というより、`this`は`Builder`クラスの中にいるので**`Builder`自身のインスタンス**を指す。値を1つずつ渡すのではなく、`Builder`インスタンスをまるごと1個の引数として`NutritionFacts`のコンストラクタに渡し、中身の取り出しは受け取った側(コンストラクタ)に任せている。

具体的には、`servingSize`(必須)、`servings`(必須)、`calories`/`fat`/`sodium`/`carbohydrate`(任意、メソッドチェーンで書き換わる)という6フィールドを持った、その時点での`Builder`インスタンス自身を指す。

<br>

**Q. `private NutritionFacts(Builder builder) { servingSize = builder.servingSize; ... }`でthisを書いていないのはエラーにならないか?**

エラーにならない。`this.`が必須になるのは、左辺の変数名と代入したいフィールド名が同じ名前で衝突している場合だけ。ここでは左辺`servingSize`は素直に「今作っているNutritionFactsインスタンス自身のフィールド」を指し、右辺`builder.servingSize`は引数`builder`が持つフィールドに明示アクセスしている。引数名が`builder`(フィールド名とは別物)なので衝突が起きておらず、`this.`を書かなくても誤解の余地がない。

もし引数名がフィールド名と同じ(例: `public NutritionFacts(int servingSize)`)であれば、`this.servingSize = servingSize;`のように`this.`が必須になる。

<br>

**Q. Pizza(継承)の例で出てくるrequireNonNull、noneOf、self、cloneが分からない。**

- `Objects.requireNonNull(x)`: nullチェック用ヘルパー。nullなら`NullPointerException`を投げ、そうでなければそのまま返すだけ。
- `EnumSet.noneOf(Topping.class)`: 「`Topping`というenumの要素を1つも含まない空の`EnumSet`を作る」という意味。`new ArrayList<>()`のEnumSet版。
- `self()`: 標準ライブラリのメソッドではなく、この本独自の設計テクニックの名前。継承先でもメソッドチェーンが正しい型でつながるようにするための回避策(シミュレートされたself型イディオム)、高度なテクニック。
- `.clone()`: 配列やコレクションの複製を作るメソッド。Item50(防御的コピー)に関連。

Pizza(継承)の例はItem2の中でも最も難しい部分で、実務でも大規模なライブラリ設計くらいでしか使わない高度なテクニック。今の段階では基本のBuilderパターン(NutritionFactsの例)の理解で十分と判断し、深追いせずItem3に進む方針にした。再訪するならItem30(ジェネリックメソッド)の後が理解しやすい。
