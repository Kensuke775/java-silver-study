# Chapter2 コーチング記録

## Item 1: Consider static factory methods instead of constructors(コンストラクタより静的ファクトリメソッドを検討する)

**教科書の例:**

```java
// Boolean.javaより
1  public static Boolean valueOf(boolean b) {
2      return b ? Boolean.TRUE : Boolean.FALSE;
3  }
```

**説明したポイント**

- クラスのインスタンスを取得する方法は「public コンストラクタ」だけではない。**staticファクトリメソッド**(インスタンスを返すだけのstaticメソッド)という選択肢がある。

- `Boolean.valueOf(boolean)`は毎回新しいオブジェクトを作らず、あらかじめ用意された`Boolean.TRUE`/`Boolean.FALSE`を返す。

- GoFの「Factory Method パターン」とは別物(名前が似ているだけ)。

<br>

**staticファクトリメソッドの5つの利点**

1. **名前を持てる**: コンストラクタは常にクラス名固定。`BigInteger(int, int, Random)`より`BigInteger.probablePrime(...)`の方が「何を返すか」が分かりやすい。同じシグネチャのコンストラクタは1つしか作れないが、staticファクトリなら名前で区別できる。

2. **呼び出すたびに新規インスタンスを作らなくてよい**: キャッシュ・使い回しが可能(`Boolean.valueOf`が好例)。不変クラス(Item17)や、`a.equals(b)`なら`a == b`が保証されるインスタンス制御クラスを作れる。

3. **戻り値の型のどんなサブタイプでも返せる**: コンストラクタは自分自身の型しか返せないが、staticファクトリは戻り値の型を実装クラスとして公開せずに返せる(例: `java.util.Collections`が45個の非公開実装クラスをstaticファクトリ経由で提供)。

4. **入力パラメータに応じて返すクラスを呼び出しごとに変えられる**: `EnumSet`の例 — enumの要素数が64以下なら`RegularEnumSet`、65以上なら`JumboEnumSet`を内部で使い分けるが、クライアントはそれを意識しない。

5. **メソッドを書く時点で、返すクラスが存在していなくてもよい**: サービスプロバイダフレームワーク(JDBCなど)の基盤。`ServiceLoader`(Java6〜)が汎用実装を提供。

<br>

**staticファクトリメソッドの2つの欠点**

1. **public/protectedコンストラクタを持たないクラスはサブクラス化できない**(Collections Frameworkの実装クラス群など)。ただしこれは合成(Item18)を推奨する・不変型(Item17)には必須、という意味で「かえって良い制約」とも言える。

2. **プログラマから見つけにくい**: コンストラクタのようにAPIドキュメント上で目立たない。命名規約(`from`, `of`, `valueOf`, `instance`/`getInstance`, `create`/`newInstance`, `getType`, `newType`, `type`)に従うことで軽減する。

<br>

**セクションの核心**

コンストラクタとstaticファクトリメソッドはどちらも一長一短がある。「反射的にpublicコンストラクタを用意する」のではなく、まずstaticファクトリの選択肢を検討すべき、というのがItem1の結論。特に「名前を持てる」「インスタンス制御できる」「戻り値のサブタイプを自由に選べる」の3点が実務上のメリットとして大きい。

## 疑問

<br>

**Q. `Boolean.TRUE`/`Boolean.FALSE`って何?**

`Boolean`クラスがあらかじめ用意している「使い回し用の定数インスタンス」。

```java
1  public final class Boolean {
2      public static final Boolean TRUE = new Boolean(true);
3      public static final Boolean FALSE = new Boolean(false);
4
5      public static Boolean valueOf(boolean b) {
6          return b ? Boolean.TRUE : Boolean.FALSE;
7      }
8  }
```

`boolean`は`true`/`false`の2種類しかないので、対応する`Boolean`オブジェクトも2個(`TRUE`と`FALSE`)だけ先に作っておき、`valueOf`はそのどちらかを毎回使い回して返す。`new Boolean(true)`を2回呼ぶと別インスタンスになり`==`は`false`だが、`valueOf`経由なら同じインスタンスが返るので`==`は`true`になる。

<br>

**Q. `final class Boolean`というのを作っておいて、それを使い回してtrue/falseを決める、ということ?**

少し違う。`Boolean`という**クラス自体**(finalは「これ以上サブクラス化できない」という意味で使い回しとは無関係)は1個の設計図でしかない。その設計図から`true`用・`false`用のインスタンスを**1個ずつ**あらかじめ作っておき(`TRUE`と`FALSE`)、`valueOf`はその2個のうちどちらかを配って返しているだけ。

「クラスを使い回す」のではなく「trueとfalse専用のオブジェクトをそれぞれ1個ずつ用意して配り回す」が正確な理解。

<br>

**Q. true/falseもオブジェクトを作らないとダメなのか?Javaって。**

プリミティブ型の`boolean`(小文字)ならオブジェクト不要。ラッパークラスの`Boolean`(大文字)を使うときだけオブジェクトが必要。

```java
1  boolean flag = true;        // プリミティブ型:オブジェクトではない、ただの値
2  Boolean obj = Boolean.TRUE; // 参照型(ラッパークラス):オブジェクト
```

`List<Boolean>`のようにジェネリクス/コレクションはプリミティブ型を直接扱えず、オブジェクト(参照型)しか入れられないため、そういう場面でラッパークラスの`Boolean`(オブジェクト)が必要になる。普段の`if (flag)`のような単純な条件分岐では`boolean`のままで十分。

<br>

**Q. staticファクトリメソッドって何?(そもそも分かっていない)**

普段の`new`の代わりに使える別の作り方。クラスの中に「オブジェクトを作って返すだけのstaticメソッド」を自分で用意する。

```java
1  public class Dog {
2      private Dog() { }                // newで直接作れないようにする
3
4      public static Dog createDog() {  // これがstaticファクトリメソッド
5          return new Dog();
6      }
7  }
8
9  Dog dog = Dog.createDog();   // newではなく、このメソッド経由で作る
```

「`new`で直接作る」代わりに「インスタンスを作って返す専用メソッドを経由する」だけの仕組み。`Boolean.valueOf(true)`や`List.of(1, 2, 3)`は実際にこの仕組みを使っている。

<br>

**Q. Booleanは新規インスタンスを作らなくて済むからメモリ効率がいいと分かったが、普通のインスタンス(例のDog/createDog)はどの利点に当たるのか?**

上のDog例自体はどの利点も示していない、ただの仕組みの説明。5つの利点は**クラスの性質によってどれが効くか変わる**もので、全部が毎回当てはまるわけではない。例えば「名前を区別したい」場面なら利点1が効く。

```java
1  public class Dog {
2      private String breed;
3      private Dog(String breed) { this.breed = breed; }
4
5      public static Dog createPoliceDog() {
6          return new Dog("German Shepherd");
7      }
8
9      public static Dog createGuideDog() {
10         return new Dog("Labrador");
11     }
12 }
```

コンストラクタは名前が`Dog`固定なので警察犬用・盲導犬用を区別できないが、staticファクトリなら`createPoliceDog()`/`createGuideDog()`と名前で意図を表現できる(利点1)。Boolean(利点2)のような「使い回し」は、値の種類が少ないクラス限定で、犬種や名前が毎回違うDogのようなクラスには基本当てはまらない。

<br>

**Q. 5つの利点をもう一度、1から5まで整理して説明してほしい。**

`User`クラスを題材に1つずつ整理。

<br>

*利点1: 名前を持てる*

```java
1  public class User {
2      private String name;
3      private boolean isAdmin;
4
5      private User(String name, boolean isAdmin) {
6          this.name = name;
7          this.isAdmin = isAdmin;
8      }
9
10     public static User createNormalUser(String name) {
11         return new User(name, false);
12     }
13
14     public static User createAdminUser(String name) {
15         return new User(name, true);
16     }
17 }
```

`new User("田中", true)`だとtrueが何を意味するか読み取れないが、`User.createAdminUser("田中")`なら「管理者ユーザーを作っている」と一目で分かる。

<br>

*利点2: 呼び出すたびに新しいインスタンスを作らなくてよい*

```java
1  public class Status {
2      public static final Status ACTIVE = new Status("active");
3      public static final Status INACTIVE = new Status("inactive");
4
5      private String label;
6      private Status(String label) { this.label = label; }
7
8      public static Status of(boolean active) {
9          return active ? ACTIVE : INACTIVE;
10     }
11 }
```

「有効/無効」のように取りうる値の種類が少ない場合、あらかじめ用意した2個を使い回してメモリ効率を上げられる(Booleanと同じ理屈)。名前や年齢が毎回違うUserには使えない。

<br>

*利点3: 戻り値の型の、どんなサブタイプでも返せる*

```java
1  public interface Payment {
2      void pay();
3  }
4
5  public class PaymentFactory {
6      public static Payment of(String method) {
7          if (method.equals("card")) {
8              return new CardPayment();   // Paymentの実装クラスA(非公開でも良い)
9          } else {
10             return new BankPayment();   // Paymentの実装クラスB(非公開でも良い)
11         }
12     }
13 }
14
15 Payment p = PaymentFactory.of("card");
```

戻り値の型を`Payment`(インタフェース)と宣言しつつ、中身では`CardPayment`/`BankPayment`という具体的な実装クラスを使い分けて返せる。コンストラクタは自分自身の型しか返せないため、これはstaticファクトリメソッド特有。

<br>

*利点4: 入力によって、返すクラスを呼び出しごとに変えられる*

利点3の例(`PaymentFactory.of("card")`と`.of("bank")`)がそのまま該当。同じメソッドなのに引数次第で内部的に返すクラスが変わる。利点3(サブタイプを返せる可能性)と利点4(実際に呼び出しごとに変わる)はセットで語られることが多い。

<br>

*利点5: メソッドを書く時点で、返すクラスが存在していなくてもよい*

```java
1  public interface PaymentProvider {
2      Payment create();
3  }
4
5  // PaymentFactoryを書いた時点では、まだどんな決済会社が
6  // 参入してくるか分からなくてもよい。
7  ServiceLoader<PaymentProvider> loader = ServiceLoader.load(PaymentProvider.class);
```

`PaymentFactory`を書いている段階で将来の決済会社の参入を知らなくても、あとから`PaymentProvider`実装クラスを追加登録するだけで既存コードを変更せず拡張できる(JDBCのドライバ追加と同じ仕組み)。プラグイン機構を設計するときの発想として重要。

<br>

*まとめ*: 利点1と3はほぼ全てのstaticファクトリメソッドで意識する価値があり、利点2・4・5は特定の場面(値の種類が少ない/インタフェース設計/プラグイン機構)でだけ効いてくる。

<br>

**Q. Payment例について。インタフェースの実装で「pay()を持つことを守る」というのは分かった。ただメソッドの戻り値としてPaymentを返す、というのが引っかかる。戻ってくる型がインスタンスなら、それに合った何かをPaymentの中で定義しなきゃいけないのでは?特に何も書かずにpay()だけで、それってPayment型なんですか?**

`Payment`側に追加の定義は一切不要。`implements Payment`して中の`void pay()`という約束(シグネチャ)さえ守れば、それだけで`CardPayment`は正式に`Payment`型として扱われる。

`Payment`は「これだけは持ってて」という条件が1個書かれているだけの空っぽの契約書(チェックリスト)。

```java
1  public interface Payment {
2      void pay();      // 条件: pay()というメソッドを持っていること
3  }
```

`CardPayment`が`implements Payment`して実際に`void pay()`を用意した時点で、コンパイラは「条件を満たしている、`Payment`型と認めよう」と判定する。

```java
1  public class CardPayment implements Payment {
2      @Override
3      public void pay() {
4          System.out.println("カード決済を実行");
5      }
6  }
```

`Payment`側に`CardPayment`用の情報を書き足す必要はどこにもない。もし`pay()`の実装を忘れたら、その時点でコンパイルエラーになる——それが唯一のチェックポイント。

<br>

**Q. メソッドでPayment型を返す、というのがまだ分からない。もしかして`implements Payment`すると、実装したクラスのインスタンスがPayment型を返せるようになるということ?だから`new CardPayment()`や`new BankPayment()`は、implements Paymentしてるから、Payment型の扱いになるということですかね?**

その理解で完全に合っている。`class CardPayment implements Payment`と書いた時点で、`CardPayment`は同時に2つの型を持つ。

- 本来の型: `CardPayment`
- 実装したことで得た型: `Payment`

```java
1  CardPayment c = new CardPayment();   // OK: 本来の型
2  Payment p = new CardPayment();       // OK: implementsしたことでPayment型としても扱える
```

これを踏まえると:

```java
20     public static Payment of(String method) {   // 戻り値の型はPayment
21         if (method.equals("card")) {
22             return new CardPayment();             // でも実際に返してるのはCardPaymentのインスタンス
23         } else {
24             return new BankPayment();              // こっちはBankPaymentのインスタンス
25         }
26     }
```

`of(...)`は「戻り値の型はPaymentですよ」と宣言しつつ(20行目)、中身では`CardPayment`/`BankPayment`という具体的なクラスのインスタンスを作って返している(22, 24行目)。コンパイルエラーにならないのは、`implements Payment`しているから`CardPayment`のインスタンスが`Payment`型としても通用するため。呼び出し元には「厳密にはCardPaymentかBankPaymentのどちらかだが、共通のPaymentという型としてだけ見せている」という動き。これがItem1の利点3(戻り値の型のどんなサブタイプでも返せる)の正体。

<br>

**Q. `@Override`って書くのは慣習ですか?**

はい、書かなくても動くが、書くのが強く推奨される慣習。

```java
1  public class CardPayment implements Payment {
2      @Override              // このアノテーション
3      public void pay() {
4          System.out.println("カード決済を実行");
5      }
6  }
```

`@Override`を消しても動作は変わらない。これはコンパイラに「このメソッドは親(インタフェースや親クラス)のメソッドをオーバーライドしているつもり」と伝えるだけの目印。目的はタイプミスの検出:

```java
1  public class CardPayment implements Payment {
2      @Override
3      public void Pay() {   // "pay"のつもりが"Pay"(大文字P)になっている
4          System.out.println("カード決済を実行");
5      }
6  }
```

- `@Override`が**なければ**: コンパイルエラーにならず、単に別の新しいメソッド`Pay()`として静かに追加されてしまう。`pay()`は実装されないまま放置され、実行時までバグに気づけない。
- `@Override`が**あれば**: コンパイラが「`Pay()`は親のどのメソッドもオーバーライドしていない」と即座にコンパイルエラーにしてくれる。

実務では「インタフェース/親クラスのメソッドを実装・上書きするときは必ず`@Override`を付ける」がほぼ確実に守られる慣習。ちょうどこの本のItem40(`Consistently use the Override annotation`)で改めて1項目として扱われる。

<br>

**Q. `of`は慣習ですか?**

はい、Javaの文法上の決まりごとではなく命名慣習。Item1の命名パターンの1つ。

| 名前 | 意味 | 例 |
|---|---|---|
| `of` | 複数の引数を1つにまとめてインスタンスを作る | `EnumSet.of(JACK, QUEEN, KING)` |
| `from` | 別の型から変換してインスタンスを作る | `Date.from(instant)` |
| `valueOf` | `from`/`of`より丁寧な言い方 | `BigInteger.valueOf(100)` |
| `getInstance`/`instance` | パラメータに応じたインスタンスを返す | `StackWalker.getInstance(options)` |

`PaymentFactory.of("card")`の`of`は文法的には別の名前(`createPayment`など)でも動くが、「複数の値から何かを組み立てて返す」という意味合いを伝えやすくするために慣習的に選ばれている。`List.of(...)`, `Set.of(...)`, `Map.of(...)`など標準ライブラリでもよく使われる名前。
