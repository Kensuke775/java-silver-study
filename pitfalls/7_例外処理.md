# 落とし穴7：例外処理

基本ルールに対する例外パターン・引っかかりやすいポイントだけを集めたメモ。問題演習で見つけたものを都度追加していく。`pitfalls/`配下に章ごとのファイルを置く構成。

<a id="pitfall-autocloseable-missing"></a>
## 1. `close()`メソッドがあっても、`implements AutoCloseable`が無ければtry-with-resourcesで使えない

原本7-10より。

```java
class MyResource {
    public MyResource() { System.out.print("C"); }
    public void close() { System.out.print("D"); }
}
```

`close()`メソッド自体は存在しているのに、`class MyResource { ... }`に**`implements AutoCloseable`（または`Closeable`）の宣言が無い**と、`try (MyResource resource = new MyResource())`の行で**コンパイルエラー**になる。

Javaは「`close()`という名前のメソッドさえあれば自動でリソース扱いする」という構造的（ダックタイピング的）な判定はしない。**明示的に`implements`しているかどうか**だけを見る。

**修正方法**：`class MyResource implements AutoCloseable { ... }`と、`implements`を1つ足すだけでよい。`close()`メソッドの中身は変更不要（`void close()`は`AutoCloseable`が要求する`void close() throws Exception`より狭い宣言なので、オーバーライドのルール上問題ない）。修正後は`open→close→finally`の順で`CADB`が出力される（`javac`+`java`で検証済み）。

**問題64での追加確認**：`class Cache implements Named { ... }`のように、`close()`があっても**無関係な別のインターフェース**を実装しているだけでは、当然`AutoCloseable`扱いにはならず、同じくコンパイルエラーになる。「何かインターフェースを実装していればOK」ではなく、**`AutoCloseable`（かそのサブインターフェース）を実装しているかどうか**がすべて。

<a id="pitfall-try-with-resources-alone"></a>
## 2. try-with-resourcesは、catch・finallyが無くても単体で成立する

問題56より。

普通の`try`ブロックは、`catch`か`finally`のどちらかが**最低1つ必要**（`try`単体は無効、コンパイルエラー：「'try'への'catch'、'finally'またはリソース宣言がありません」）。

```java
try {
    System.out.println("body");
}
// ↑ catch/finally無し + リソース宣言も無し → コンパイルエラー
```

しかし、**リソース宣言があれば、それ単体で"最低1つ"の条件を満たす**——catch・finallyが両方無くてもコンパイルが通る。

```java
try (Logger a = new Logger("A")) {
    System.out.println("body");
}
// ↑ catch/finally無しでもOK。リソース宣言自体が「必ずcloseする」という意味のある処理だから
```

**正確なルール**：`try`には「`catch`」「`finally`」「**リソース宣言**」のうち最低1つが必要。2.1で習った「catch/finallyのどちらか必須」は、リソース宣言というもう1つの選択肢を見落としていた。

<a id="pitfall-multi-resource-partial-autocloseable"></a>
## 3. 複数リソースのうち1つでもAutoCloseable未実装なら、他が正しく実装されていても全体がコンパイルエラーになる

問題65より。

```java
try (Logger log = new Logger(); Cache cache = new Cache()) {
    System.out.print("Use");
}
class Logger implements AutoCloseable { ... }  // 正しく実装
class Cache { ... }                             // implementsが無い
```

`Logger`は`AutoCloseable`を正しく実装しているが、`Cache`が実装していないため、**`Cache`だけが無視されて`Logger`だけ動く、ということにはならず、その行全体がコンパイルエラーになる**。try-with-resourcesの複数リソース宣言は、1つでも型条件を満たさない要素があれば、宣言全体が不成立になる。

---

<a id="pitfall-close-signature-must-match-exactly"></a>
## 4. `implements AutoCloseable`と書いても、引数無し`close()`を正しく実装しないと契約不成立（オーバーロードでは代用不可）

問題66より。

```java
class Session implements AutoCloseable {
    public Session() { System.out.print("Open"); }
    public void close(int code) { System.out.print("Close" + code); }  // ← これは別物
}
```

`AutoCloseable`が要求するのは**厳密に「引数ゼロ個の`close()`」**というシグネチャ。`close(int code)`は名前が同じでも**引数の数が違う別メソッド（オーバーロード）**であり、契約を満たしたことには一切ならない。

このコードは二重にエラーになる：
1. `Session`自身が、`AutoCloseable`の抽象メソッド`close()`を実装していない（`abstract`にしない限りクラス宣言自体がエラー）
2. `try(...)`の呼び出し側も、引数無し`close()`が存在しないため別途エラーになる

**ただし、オーバーロードを"追加"すること自体は問題ない**。以下は正しくコンパイルが通る：

```java
class Session implements AutoCloseable {
    private int code;
    public Session() { this.code = 99; System.out.print("Open"); }

    @Override
    public void close() {        // ← 契約を満たす本体(これが無いと動かない)
        close(code);               // ← 内部でオーバーロード版に委譲するのは自由
    }

    public void close(int code) {  // ← 追加のオーバーロード。契約とは無関係
        System.out.print("Close" + code);
    }
}
```

**try-with-resourcesが自動で呼ぶのは、常に引数無しの`close()`だけ**。オーバーロード版（`close(int)`など）が自動的に呼ばれることは原理的にあり得ない——コンパイラはどの引数を渡せばいいか判断できないため。

<a id="pitfall-import-vs-fqn"></a>
## 5. `import`を忘れると、短い名前は使えない（完全修飾名なら`import`不要）

`sample/chap7/ex12/Main.java`より。

```java
public class Main {
    public static void main(String[] args) throws FileNotFoundException {  // ← importが無い！
        load();
    }
    static void load() throws java.io.FileNotFoundException {  // ← こっちは完全修飾名なのでOK
        throw new java.io.FileNotFoundException();
    }
}
```

```
エラー: シンボルを見つけられません
    public static void main(String[] args) throws FileNotFoundException {
  シンボル:   クラス FileNotFoundException
```

**`java.io.FileNotFoundException`のように「パッケージ名+クラス名」をそのまま書く形を完全修飾名（FQN）と呼び、`import`が無くても常にこの形なら使える。** `import java.io.FileNotFoundException;`は、この完全修飾名を毎回書く代わりに**短い名前（`FileNotFoundException`）だけで済ませるための省略記法**でしかない。

同じファイル内で「短い名前」と「完全修飾名」が混在していると、**完全修飾名の方は問題なくコンパイルが通るのに、短い名前の方だけ`import`忘れでエラーになる**——という気づきにくい非対称な失敗パターンになる。エラーメッセージが「型が違う」ではなく「シンボルが見つからない」なので、catch-or-declareのルールの問題だと誤解しやすい点も要注意。

<a id="pitfall-indexoutofbounds-hierarchy"></a>
## 6. `ArrayIndexOutOfBoundsException`は知っていても、親の`IndexOutOfBoundsException`自体が飛ぶ場面を見落としがち

会話中の質問より。

```
IndexOutOfBoundsException
├── ArrayIndexOutOfBoundsException   ← 配列でアクセス範囲外
└── StringIndexOutOfBoundsException  ← 文字列でアクセス範囲外
```

配列・文字列は専用のサブクラスが飛ぶが、**`List`（`ArrayList`など）の`get(int)`や`add(int, E)`は、サブクラス化されておらず`IndexOutOfBoundsException`自身が直接飛ぶ**。「配列＝Array系、List＝IndexOutOfBounds自身」という非対称さが地味な引っかけになる。

| 場面 | 具体例 | 投げられる型 |
|---|---|---|
| 配列 | `int[] a = new int[3]; a[3]` | `ArrayIndexOutOfBoundsException` |
| 文字列 | `"abc".charAt(5)` | `StringIndexOutOfBoundsException` |
| List | `new ArrayList<String>().get(0)` | `IndexOutOfBoundsException` |

[問題7-4復習](../chapter7_practice/problems_v2.md#q7-4-review)で確認した「キャッチできるのは自分自身の型かその祖先型」のルールがここでも効く——`catch (IndexOutOfBoundsException e)`と書けば、配列由来・文字列由来どちらの例外も祖先型として一括でキャッチできる。

<a id="pitfall-throws-vs-multicatch-overlap"></a>
## 7. `throws`句は親子関係の型を並べてもOK、multi-catchは逆に親子関係だとNG

原本7-9より。会話中の質問で発覚。

```java
// throws句：親(IOException)と子(FileNotFoundException)を両方書いてもコンパイル成功
void test() throws IOException, FileNotFoundException {
    throw new FileNotFoundException();
}
```

```java
// multi-catch：同じ親子関係を「|」で並べるとコンパイルエラー
catch (IOException | FileNotFoundException e) {
```
```
エラー: 複数catch文の代替をサブクラス化によって関連付けることはできません
代替FileNotFoundExceptionは代替IOExceptionのサブクラスです
```

**`throws`句は「投げる可能性のある型を宣言するリスト」なので、祖先型と子孫型が両方入っていても単に子孫側が冗長なだけでエラーにはならない**（原本7-9の選択肢D「`FileNotFoundException, ClassNotFoundException`」のように、余分な型を足しても問題ない理屈と同じ）。

一方**multi-catch（`catch (A | B e)`）は、`|`で並べた型同士が祖先子孫の関係にあることを専用ルールで禁止している**——片方がもう片方に完全に飲み込まれて意味を持たないため。`javac`で検証済み（エラーメッセージ「複数catch文の代替をサブクラス化によって関連付けることはできません」）。

**同じ「親子関係を含む」状況でも、`throws`とmulti-catchでルールが逆になる**点が引っかけどころ。

<a id="pitfall-error-can-be-thrown"></a>
## 8. `Error`も構文的には普通に`throw`・`catch`できる（実務で自分から投げることは稀なだけ）

会話中の質問より。

```java
try {
    throw new AssertionError("ここには来ないはずの状態");
} catch (Error e) {
    System.out.println("catch(Error)でキャッチ: " + e.getMessage());
}
```
`javac`+`java`で検証済み。`throw new Error(...)`も`catch(Error e)`も、構文・実行のどちらも普通に成立する。「`Error`は特別な仕組みで、`throw`や`catch`の対象にできない」という誤解に注意。

**ただし実務で自分のコードから明示的に投げる場面はほぼ無い**——`Error`系は「JVM自身がもう正常続行できないと判断したときに自動的に投げるもの」という位置づけが基本：

| Errorの種類 | 誰が投げるか |
|---|---|
| `StackOverflowError` | JVMが自動（無限再帰など） |
| `OutOfMemoryError` | JVMが自動（メモリ枯渇） |
| `NoClassDefFoundError` | JVMが自動（クラスロード失敗） |
| `AssertionError` | プログラマが手動で投げる**唯一の例外的存在**（`assert`文の失敗時、または「絶対来ないはずのコードパス」への防御的な明示throw） |

[問題75](../chapter7_practice/problems_v1.md)で確認した「オーバーライド時のthrows narrowingルールが`RuntimeException`だけでなく`Error`にも及ばない（どちらも自由に追加できる）」というルールと合わせて、`Error`は「投げる側の責任」というより「JVMが投げてくるものを（基本何もせず）通過させる」だけの存在だと理解しておくと迷わない。
